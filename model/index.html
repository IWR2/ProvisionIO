    Data Model Overview

    The ProvisionIO API utilizes a high-performance Single-Table Design in AWS DynamoDB. By consolidating all business entities into one table, we optimize for speed, query efficiency, and cost.

    Storage Strategy

    All entities reside in a single table, differentiated by EntityType and EntityId attributes.

    • Partition Key: EntityId (String)
    • Sort Key: EntityType (String)
    • Prefixes:
      • Clients: Client#
      • Services: Service#
    • Statistics: Atomic tracking (CLIENT_COUNT and SERVICE_COUNT) via transactions ensures data consistency during creation and deletion.

    Indexing Strategy

    Three Global Secondary Indexes (GSIs) are configured to support application queries:

    Index Name Partition Key Sort Key Purpose
    TypeIndex EntityType EntityId Retrieves all items of a specific category (Services, Clients).
    OwnerIndex owner EntityId Finds all clients assigned to a specific Auth0 user.
    ClientServiceIndex clientId EntityId Finds all services belonging to a specific client.

    Entity Definitions

    Users are managed externally via Auth0 and are not stored in the database.

    Property Type Notes
    id string Unique user_id from Auth0 (e.g., auth0|0123)

    Relationships:

    • User-Client (1:M): A user can own 0 or multiple Clients.
    • Ownership: A Client must have exactly one assigned owner (the Auth0 user_id).

    Security & Access:

    • Data Isolation: All API operations enforce ownership by validating the authenticated user's sub claim against the Client's owner attribute.

    The Client entity represents an organization or user-owned account.

    Property Type Notes
    id string Unique UUID generated by the backend (e.g., e1622f97-f6dd...).
    name string The client’s name.
    contact_manager string The client’s contact manager.
    email string The client’s email. Must be in valid email format.
    owner string Auth0 user_id (sub claim) identifying the assigned owner.
    self string The self-referencing API link.

    Relationships:

    • User-Client (M:1): A user (from Auth0) can own 0 or many Clients. A Client must have exactly one owner.
    • Client-Service (1:M): A Client can have 0 or many Services. A Service can be associated with 0 or 1 Client. This is not stored as an array; instead, it is queried via the ClientServiceIndex GSI using the service's clientId attribute.
    • Ownership: Clients are linked to Auth0 users via the owner attribute, which maps directly to the user's Auth0 sub (subject) ID.

    Assignments & Security:

    • Atomic Assignments: Services are linked to Clients via the clientId attribute. Assignments are protected by atomic ConditionExpression checks in DynamoDB to ensure a service cannot be overwritten while already assigned.
    • Ownership Enforcement: The API enforces strict ownership checks; a service can only be assigned to a client if the requesting user owns that client.

    Individual cloud resources linked to a client.

    Property Type Notes
    id string Unique UUID generated by the backend (e.g., e1622f97-f6dd...).
    name string The name of the service.
    type string The type of the service.
    price float The monthly cost in USD; must be non-negative.
    clientId string The UUID of the assigned client, or null if unassigned.
    self string The self-referencing API link.

    Relationships:

    • Service-Client (M:1): A Service can be associated with at most one Client; a Client can have zero or multiple Services.
    • Ownership: Services are associated with clients via the clientId attribute. This is indexed via the ClientServiceIndex GSI to allow efficient retrieval of all services for a specific client.

    Assignments & Security:

    • Atomic Assignments: Assignments are protected by atomic ConditionExpression checks in DynamoDB to ensure a service cannot be overwritten while already assigned.
    • Ownership Enforcement: The API enforces strict ownership checks; a service can only be assigned to a client if the requesting user owns that client.
